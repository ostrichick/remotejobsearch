# RoleScout 운영·복구 점검표

기준: 2026-09-21. 코드와 로컬 모의 테스트에서 확인한 사항과 **실제 Sites 배포에서 확인해야 할 사항**을 구분한다. 이 문서와 스크립트는 배포, 원격 데이터 접근, 실제 인증 검증을 수행하지 않는다.

## 1. 인증 경계: 로컬과 운영은 별도 검증

- 개발 모드 `vite.config.ts`: 첫 번째 미들웨어가 요청의 `oai-authenticated-user-*` 헤더를 파싱 헤더와 원본 헤더에서 제거한다. 이후 설치된 `@openai/sites-vite-plugin`이 로컬 호스트·루프백 접속 및 모의 로그인 쿠키를 확인하여 고정 테스트 계정 `local_seedy`를 삽입한다. API 프록시는 첫 미들웨어를 통과한 요청 중 해당 모의 ID·이메일·루프백 접속 조건을 충족하는 요청만 전달하며, 헤더 전달 목록도 제한한다.
- `tests/dev-auth.test.ts`는 **실제 로컬 Vite 서버**에서 비로그인 위조 ID가 401을 받는지, 로컬 로그인으로 `/api/me`가 동작하는지, 로그인한 상태에서 다른 ID를 보내도 테스트 계정이 유지되는지 검증한다. `npx tsx --test tests/dev-auth.test.ts`를 다른 D1/Wrangler 테스트와 동시에 실행하지 않는다.
- 로컬 Sites 로그인은 단순한 `__sites_local_auth=1` **개발용 모의 쿠키**다. 암호학적 세션 검증이 아니므로 외부에 개발 서버를 공개하거나 실제 개인정보를 이용해 보안성을 평가하지 않는다. 테스트 결과만으로 운영 환경의 `oai-authenticated-user-id` 헤더 출처를 신뢰했다고 판정하지 않는다.
- **배포 전 필수:** 실제 Sites HTTP dispatch가 클라이언트가 보낸 `oai-authenticated-user-*`를 제거하고 인증된 계정의 고유 식별자로 재설정하는지 플랫폼 공식 동작 및 실제 두 계정의 요청으로 확인한다. 해당 확인 없이 운영 인증 격리가 검증됐다고 표기하지 않는다. 운영에서 개발용 `local_seedy`를 실제 사용자 ID로 대체하거나 자체 생성하지 않는다.

### 실제 운영 2계정 검증 절차 — 테스트 데이터만 사용

1. 서로 다른 ChatGPT 계정 A/B로 별도 브라우저 프로필 또는 완전히 분리된 세션을 연다. 각자의 `/api/me` 응답과 로그인 화면을 기록하되, 쿠키·토큰·이메일·원본 이력서는 공유 로그에 넣지 않는다.
2. 계정 A에 고유한 테스트 프로필·저장 공고·공고 품질 평가와 메모를 만들고, B에는 다른 테스트 값을 저장한다. 각각 새로고침한 뒤 자신의 프로필·저장 목록·평가 내역만 보이는지 확인한다.
3. A의 로그인 세션에서 브라우저 개발자 도구를 사용해 B의 테스트 ID를 `oai-authenticated-user-id` 요청 헤더에 수동 지정한 `/api/profile` 요청을 보낸다. B의 데이터가 반환되지 않고 A의 권한이 유지되거나 요청이 거부되어야 한다. 동일하게 B→A를 검사한다. 헤더가 브라우저나 호스트에서 차단되어 테스트 자체가 불가능했다면 **미검증**으로 기록한다.
4. 로그인하지 않은 별도 세션에서 임의 신원 헤더만 추가한 `/api/profile`·`/api/me` 요청은 인증되지 않아야 한다. A/B의 상태가 섞이지 않는지 새로고침·재로그인을 반복 확인한다.
5. B 계정의 평가를 만들고 수정·삭제한 뒤 A의 평가가 유지되는지 확인한다. 개인 평가의 CSV/JSON 내보내기는 기본적으로 메모가 제외되고, 별도 선택한 경우에만 포함되는지 점검한다. 이어 B 계정의 **테스트 데이터만** 전체 삭제하고 A의 테스트 프로필·저장 공고·평가가 유지되는지 확인한다. 테스트 완료 후 A 데이터도 정리한다. 오류가 발생하면 출시를 보류하고 실제 응답·요청 흐름을 민감정보를 지운 형태로 기록한다.

## 2. 로컬 D1 + R2 오프라인 백업

`scripts/backup-local.ps1`는 지정한 **로컬** `.wrangler\state\v3` 디렉터리 전체를 복사한다. D1 SQLite 본체와 WAL/SHM, R2 메타데이터와 블롭을 함께 보존하므로, 단순한 SQL 내보내기보다 현재 로컬 Miniflare 상태를 통째로 보존한다. `job_evaluations`에 저장된 개인 평가·선택 메모도 D1 백업에 포함되며 별도의 익명화된 보고서로 간주할 수 없다. 각 파일의 SHA-256과 크기를 검사한 뒤에만 `manifest.json`을 작성한다. manifest가 없으면 불완전한 백업이며 복구 스크립트가 거부한다. 원격 Cloudflare DB/R2를 호출하지 않는다.

작업 전에 **`npm run dev`, Wrangler, 테스트 등 해당 로컬 상태를 열 수 있는 모든 프로세스를 종료**한다. 스크립트의 `-ConfirmStopped`는 운영자 확인 표시일 뿐, 열린 파일이나 동시 접근을 자동으로 탐지하지 않는다. 백업을 저장할 상위 폴더를 미리 만들고, 프로젝트와 `.wrangler` 외부의 접근 제한된 위치를 사용한다. 백업은 이력서·개인정보를 포함할 수 있으므로 Git, 공유 폴더, 일반 로그에 업로드하지 않는다.

프로젝트 최상위 경로에서 PowerShell 실행 예시(실제 경로는 직접 지정):

```powershell
$repo = (Resolve-Path .).Path
$source = Join-Path $repo '.wrangler\state\v3'
$parent = 'D:\Private\RoleScout-local-backups' # 사용자가 만든 프로젝트 외부 폴더
$backup = Join-Path $parent 'snapshot-20260921-unique' # 반드시 새 경로
& .\scripts\backup-local.ps1 -SourceStateDirectory $source -BackupDirectory $backup -ConfirmStopped
```

`$source`는 정확히 `.wrangler\state\v3`로 끝나는 로컬 절대경로여야 하고 그 안에 `d1`, `r2`가 있어야 한다. 백업 대상은 **아직 존재하지 않는** 절대경로여야 하며 프로젝트 안이나 원본 안에 둘 수 없다. 기존 백업 덮어쓰기·링크/정션 경유 복사·복사 중 원본 해시 변경은 거부한다. 오류 후 생성된 폴더에 `manifest.json`이 없으면 중단된 백업으로 취급하며, 운영자가 내용을 점검한 후 별도 이름으로 다시 백업한다.

## 3. 오프라인 복구 및 비파괴 리허설

`scripts/restore-local.ps1`은 복구 전에 모든 manifest 파일의 이름·크기·SHA-256과 D1/R2 포함 여부를 검사한다. **이미 존재하는 대상은 절대 덮어쓰지 않는다.** 정상 백업을 별도 *빈 경로*에 복구하고 다시 파일별 SHA-256을 검증한다. 실제 운영 데이터나 원격 서비스를 건드리지 않는다.

```powershell
$rehearsalParent = Join-Path $parent 'rehearsal\.wrangler\state'
New-Item -ItemType Directory -Path $rehearsalParent -Force | Out-Null
$target = Join-Path $rehearsalParent 'v3' # v3가 없어야 함
& .\scripts\restore-local.ps1 -BackupDirectory $backup -TargetStateDirectory $target -ConfirmStopped
```

리허설에서는 복구된 디렉터리의 D1/R2 파일 수와 해시가 원본 manifest와 일치하는지 확인한다. **이것은 오프라인 바이트 복구 검증**이며 SQLite 데이터 열기, 앱의 사용자별 읽기·쓰기 또는 원격 운영 복구까지 확인한 것은 아니다. 그런 수준의 검증은 별도 격리한 로컬 프로젝트/바인딩에서 복구본을 사용해 진행한다. 실서비스 데이터를 리허설 환경에 올리지 않는다.

실제 로컬 상태를 복구해야 한다면 모든 프로세스를 종료하고 기존 `.wrangler\state\v3`를 운영자가 수동으로 안전한 별도 경로에 보존한 뒤, 같은 경로가 **존재하지 않는 상태**에서 `-TargetStateDirectory`로 지정한다. 복구·무결성 검사가 끝난 뒤 로컬 UI와 API를 점검하고, 실패하면 복구본을 별도로 격리한 뒤 보존해 둔 기존 상태를 수동으로 되돌린다. 스크립트는 원본 삭제, 덮어쓰기, 마이그레이션 적용 또는 자동 전환을 하지 않는다. 새로운 Wrangler/Miniflare 저장소 버전과 호환되는지는 별도 확인해야 한다.
