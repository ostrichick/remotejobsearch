# 공고 수집 및 출처 신뢰도 설계

> 작성일: 2026-09-05  
> 목적: 여러 채용 사이트·원격 플랫폼의 공고를 수집하면서, 출처와 지급 관련 위험을 투명하게 표시한다.

## 1. 원칙

이 기능은 플랫폼이나 공고를 자동으로 `사기`라고 단정하지 않는다. 신뢰도는 아래의 서로 다른 질문을 분리해서 답한다.

| 질문 | 표시 필드 | 주의점 |
|---|---|---|
| 이 공고는 어디에서 왔는가? | `출처`, `원문 링크`, `수집 시각` | 플랫폼에 올라온 공고가 실제 회사가 낸 것인지는 별도 확인 필요 |
| 공고가 회사의 공식 채용 페이지와 연결되는가? | `공식 공고 일치 여부` | 일치하면 강한 긍정 근거이나, 미확인은 사기 증거가 아님 |
| 플랫폼의 지급·분쟁 보호 조건은 공개되어 있는가? | `지급·보호 정보` | 플랫폼 약관·보호 제도 존재와 개인별 실제 지급 경험은 다름 |
| 공고에 즉시 위험 신호가 있는가? | `안전 경고` | 신호 기반 주의 표시이며 법적 판정이 아님 |
| 타인의 지급·운영 경험은 어떠한가? | `외부 경험 요약` | 검증 가능한 복수 출처만 요약, 단일 리뷰는 증거로 사용하지 않음 |

## 2. 공고 수집 우선순위

| 단계 | 수집 방식 | 예시 | 허용·안정성 원칙 |
|---:|---|---|---|
| A | 공식 공개 API / ATS 피드 | Greenhouse, Lever, Ashby | API 문서·사용 약관에 맞게 호출. 원문 URL과 제공자 식별자를 저장 |
| B | 회사 공식 채용 페이지의 구조화 데이터 | 회사 careers 페이지의 `JobPosting` 구조화 데이터 | robots.txt, 이용 약관, 요청 제한을 검토하고 회사별 커넥터로 운영 |
| C | 제휴·라이선스 데이터 제공자 | 계약된 글로벌 채용 데이터 피드 | 재배포·저장·갱신 권한을 계약으로 확인 |
| D | 사용자 제보·북마크 | 사용자가 붙여넣은 공고 URL | 원문 표시와 검증 상태를 분리; 자동 대량 수집 대상으로 삼지 않음 |

**제외**: 로그인 우회, CAPTCHAs 우회, 서비스 약관·robots 정책을 무시한 대량 스크래핑, 개인 프로필 데이터 수집. 특정 사이트의 공개 페이지를 읽을 수 있다는 사실만으로 재수집·재배포 권한이 생기지는 않는다.

## 3. 테이블에 표시할 출처·안전 열

| 열 | 값 예시 | 원칙 |
|---|---|---|
| 출처 | `공식 회사 채용 페이지`, `Greenhouse`, `원격 플랫폼`, `사용자 제보` | 플랫폼명과 원문 링크를 제공 |
| 검증 수준 | `공식 원문 확인`, `공개 ATS 피드`, `제휴 피드`, `사용자 제보`, `확인 중` | 수집 경로에 관한 사실 표시 |
| 회사 공식 일치 | `일치`, `미확인`, `불일치 의심` | 회사 도메인의 동일 공고/채용 페이지 존재 여부 |
| 지급·계약 정보 | `플랫폼 에스크로/분쟁 절차 공개`, `계약 조건 미기재` | 플랫폼 공식 문서의 공개 여부와 원문 조건을 표시 |
| 안전 경고 | `없음`, `추가 확인 필요`, `강한 위험 신호` | 아래 규칙으로 도출하고 근거를 펼쳐 보여 줌 |
| 마지막 검증 | 날짜·시각 | 원문과 신뢰 근거를 마지막으로 확인한 시각 |

## 4. 안전 경고 규칙

### 4.1 즉시 강한 위험 신호

아래 항목은 공고/연락 과정에서 발견되면 `강한 위험 신호`를 표시하고, 지원자가 금전·민감정보를 제공하지 않도록 경고한다.

- 채용·교육·장비·계정 활성화·출금 등을 이유로 **선입금**을 요구
- 암호화폐, 기프트카드, 송금 등 특정 방식으로 선입금을 요구
- 수표를 입금한 뒤 일부를 송금·구매하도록 요구
- ‘업무/최적화/클릭 과제’를 시작하거나 보상을 출금하기 위해 본인 돈을 입금하라고 요구
- 면접·채용 전부터 계좌 정보, 신분증 번호 등 불필요한 민감정보를 요구

이 조건들은 FTC의 채용·부업 사기 경고에 근거한다. 특히 “일하려면 돈을 내라” 또는 가짜 수표를 현금화하고 돈을 되돌려 보내라는 요청은 강한 사기 신호다.

### 4.2 추가 확인 신호

다음은 단독으로 사기를 입증하지 않으나, 테이블에 `추가 확인 필요`로 표시한다.

- 법인명·주소·공식 도메인·업무 설명이 없거나 서로 맞지 않음
- 회사 공식 careers 페이지에서 동일 공고를 찾지 못함
- 비현실적으로 높은 보수와 매우 낮은 요구 조건을 함께 제시
- 지원을 서두르게 하거나, 상세 면접 전에 계좌·신분 정보를 요구
- 회사 도메인이 아닌 무료 이메일만을 공식 연락 수단으로 제시
- 계약 형태, 지급 시점, 업무량, 플랫폼 수수료가 모두 불분명

## 5. 플랫폼 지급 신뢰도

‘이 플랫폼에서 모두 돈을 잘 받는다’는 일반화는 데이터가 충분하지 않으면 할 수 없다. 대신 다음을 독립 지표로 기록한다.

| 지표 | 판정 방식 | 표시 예 |
|---|---|---|
| 운영 주체 확인 | 법인·도메인·연락처·공식 약관 공개 여부 | `운영 주체 공개` / `미확인` |
| 지급 구조 공개 | 지급 수단, 정산 주기, 수수료, 최소 출금액 공개 여부 | `정산 주기·수수료 공개` |
| 분쟁·에스크로 | 에스크로·분쟁 절차·환불 규칙 문서화 여부 | `분쟁 절차 공개` |
| 독립적 경험 | 복수의 독립 리뷰·포럼·규제기관 신고에서 반복되는 지급 지연/미지급 패턴 | `외부 경험 검토됨` + 출처 수·기간 |
| 회사 원문 교차 확인 | 공고가 고용주 공식 사이트에서도 확인되는지 | `공식 공고 일치` |

이 지표들은 **플랫폼 수준의 투명성**을 보여 준다. 개별 사용자의 대금 회수 가능성이나 플랫폼의 법적 안전성을 보증하지 않는다.

## 6. 데이터 모델 추가

```text
JobSource
  id, name, source_type, official_domain, terms_url, robots_checked_at
  ingestion_method, license_status, active

SourceVerification
  job_posting_id, verification_level, canonical_job_url
  official_company_match: matched | unknown | suspected_mismatch
  evidence[], checked_at

PlatformTrustAssessment
  job_source_id, assessment_version, status: transparent | limited_info | caution
  operator_disclosed, payout_terms_disclosed, dispute_process_disclosed
  independent_evidence_summary, evidence[], assessed_at, expires_at

JobSafetySignal
  job_posting_id, severity: info | caution | high_risk
  signal_type, evidence_quote_or_url, detected_at, human_review_status
```

## 7. 사람 검토와 이의 제기

- `high_risk` 표시는 자동 탐지 후에도 운영자 검토 대기 상태를 명확히 표시한다.
- 사업자·플랫폼은 근거 링크와 함께 잘못된 표시를 정정 요청할 수 있어야 한다.
- 사용자는 의심 공고·미지급 경험·성공적으로 완료한 지급 경험을 신고할 수 있지만, 단일 신고만으로 점수·표시를 바꾸지 않는다.
- 사용자 경험은 개인정보를 제거하고, 신고 상태·검토 일자·근거 수를 보여 준다.
- 금전 거래나 계약 체결 전에는 항상 회사의 독립적으로 확인한 연락처와 공식 사이트로 교차 검증하라는 안전 안내를 표시한다.

## 8. MVP 범위와 이후 단계

| 단계 | 제공 기능 |
|---|---|
| MVP | 출처·원문 URL·수집 시각, 공식 ATS 여부, 원문에 있는 계약/보수 정보, 명백한 위험 신호 경고 |
| 2단계 | 회사 공식 공고 교차 확인, 플랫폼 약관·지급 절차의 공개 여부, 사용자 신고 |
| 3단계 | 검증 가능한 복수 외부 경험의 기간별 요약, 사람 검토·이의 제기, 신뢰도 갱신 이력 |
